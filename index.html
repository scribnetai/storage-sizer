Sizing math, explained

For each pool and each year, the chain runs: grow the logical demand, shrink it by data reduction, then multiply back up through every protection layer, overhead, and headroom:

logical[y] = basis × (1+g)y compounding — or basis + y×gTB static

raw[y] = (logical[y] ÷ reduction) × (1 + snapCopies × snapSize%) × localFactor × (1 + remoteCopies) × (1 + overhead%) ÷ (1 − spare%)

Worked example — 40 TB used, 20%/yr compound for 3 years, 1.8× reduction, 1 snapshot copy at 25%, 2-way mirror, 10% overhead, 15% headroom:

Every pool in the tool shows this worked chain with your numbers plugged in — today (Year 0) and at the horizon year. The protection layer is where storage quotes are won or lost, so it gets its own explicit step.

Honest limitations

  • This is capacity sizing, not performance sizing. It doesn't model IOPS, latency, or workload behavior — validate the final spec against performance data.
  • Data-reduction ratios are planning assumptions, not measurements. Dedupe/compression is workload-dependent — validate with vendor sizing tools before quoting.
  • Snapshot retention cost is an estimate of change rate — your per-copy percentage is a judgment call.
  • Replication bandwidth and RPO aren't modeled — only the capacity footprint of the replica copies.
  • No pricing — the output is raw TB per pool per year, which your VAR tooling turns into quotes.
⚠️ Indicative math, not a quote. Array pricing, data-reduction guarantees, software licensing, and partner programs change the dollars. Use this to frame the conversation — always validate against an official quote.

Frequently asked questions

Is my data uploaded anywhere?

No. Files are read with the browser's FileReader API and parsed in memory by a vendored copy of SheetJS running in this page; manual entries never leave the form. There is no server and no network request carrying your data — check devtools' network tab, or disconnect after the page loads.

Is anything stored in my browser?

No. Everything lives in the page's JavaScript memory for the session. Nothing goes to localStorage, IndexedDB, or cookies. Hit "Clear session data" or close the tab and it's gone.

Do I need an RVTools export, or can I type numbers in?

Either. The export gives you per-cluster provisioned/used storage automatically, plus datastore totals for validation. Manual entry just needs pool-level totals: VMs, provisioned TB, used TB, and optionally current usable TB — five minutes with the customer's capacity spreadsheet.

What's a "pool"?

From an RVTools export, pools are per-cluster storage demand (datacenter / cluster) — aligned with how Server Sizer groups things. With manual entry you define your own pools, e.g. splitting by tier (flash vs capacity) or workload. One pool, one set of tunables.

Should I size on "used" or "provisioned"?

Used is actual written data — the honest footprint. Provisioned includes thin-provisioned commitments that haven't materialized yet — more conservative, and safer when the estate is thin-heavy with headroom to fill. The tool defaults to used; flip to provisioned when you want the conservative number on the quote.

What should I use for data reduction?

The 1.8× default is a middle-ground planning assumption. The rule of thumb baked into the findings: mirroring without meaningful reduction is the most expensive way to buy storage — every 0.5× of reduction improvement is worth real TB at the horizon. Vendor reduction guarantees vary by workload; validate before you quote their number.

Compounding or static growth?

Compounding applies a %/yr rate on the prior year's total — right when growth feeds on itself (organic data growth). Static adds a flat TB/yr — right when you know the number from the backup growth trend or a project pipeline. You can override the rate per pool while keeping the mode.

What's the difference between overhead and headroom?

System overhead is capacity the array consumes for itself — formatting, metadata, system reserve. Free-space headroom is slack you deliberately keep — for rebuilds, snapshot bursts, and not running the array at 100%. The tool treats overhead as a multiplier and headroom as a divisor, which is why small headroom changes move the raw number a lot.

Can I share the results with my team or the customer?

Yes — the Growth plan tab generates a standalone HTML briefing you can download and email. Fully self-contained, no external dependencies, and it contains only the analysis, which you control. Scrub customer names from pool labels first if the report leaves your org.

Does it do pricing?

No — it produces raw TB per pool per year. Your VAR quoting tooling turns that capacity plan into dollars.
